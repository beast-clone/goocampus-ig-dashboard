## 🔒 Security

### 1. Broken access control — permissions were UI-only *(High)*
- **Bug:** `hasCapability()` / `canAccessSection()` were called only in `team/page.tsx` (client). No API route checked them, so any logged-in user could `POST /api/marketing-hub/delete` (wipe any task) or `GET /api/leads-crm` (pull all sales-lead PII) by calling the endpoint directly.
- **Change:** Added server-side guards `requireCapability(cap)` / `requireSection(sec)` to **`lib/api-guard.ts`** (mirroring `admin/team`'s `requireAdmin`). Applied them:
  - `marketing-hub/delete` → `delete_tasks`
  - `marketing-hub/create` → `create_tasks`
  - `marketing-hub/update` → `edit_tasks`
  - `marketing-hub/takeover` → `edit_tasks` *(not `assign_tasks` — that would break the producer "claim" flow, since producers don't have `assign_tasks`)*
  - `marketing-hub/collaborators` (POST + DELETE) → `edit_tasks`
  - `leads-crm` (GET) → `sales` section
- **Verified:** each route returns its normal 400/405 (not 500) → compiles; `leads-crm` returns **400 (missing params), not 403**, confirming an admin passes the guard and isn't wrongly blocked. A non-capable user hits the `hasCapability → false → 403` path by logic (can't be live-tested without a non-admin login).

### 2. SSRF in the article reader *(High)*
- **Bug:** `radar/article` validated the URL and the HEAD-resolved redirect, but the final content **GET** used `redirect: "follow"` and never re-checked the post-redirect host. A server answering HEAD `200` but GET `302 → http://169.254.169.254/…` could make the server fetch cloud-metadata and return it as article text.
- **Change:** After the GET, `await assertPublicUrl(r.url || resolved)` before reading/returning the body (mirrors the sibling `radar/pdf` guard). `radar/article/route.ts`.
- **Verified:** route compiles (returns 400 on a bad URL); logic matches the already-safe `radar/pdf`.

### 3. Stored/reflected XSS in the reader *(Medium–High)*
- **Bug:** the reader returned Mozilla Readability HTML **unsanitized**; the client injects it via `dangerouslySetInnerHTML`. Readability strips `<script>` but not `on*` handlers, so `<img src=x onerror=…>` / `<svg onload=…>` fired in the authenticated dashboard origin. No DOMPurify existed anywhere.
- **Change:** Added `sanitizeArticleHtml()` in `radar/article/route.ts` (uses the already-present JSDOM — no new dependency): removes executable/embedding elements (`script,iframe,object,embed,svg,math,…`), drops every `on*` attribute, and strips `javascript:`/`vbscript:` URLs. Applied to both HTML outputs.
- **Verified:** **6/6 unit tests** against the repo's real jsdom — strips `onerror`/`onload`, removes `<svg>`/`<script>`, drops `javascript:` hrefs, preserves legit `https` images/links.

### 4. Audit-log attribution spoofing *(Low)*
- **Bug:** `actor = body.actor || getSessionUserId()` let a caller name anyone in the `mh_activity` audit rows.
- **Change:** `marketing-hub/delete` now uses `getSessionUserId()` only. **Left as-is on `marketing-hub/update`** — there `body.actor` is a real feature (My Day's "acting as switched person" attribution, per the code comment); removing it would break that. Documented trade-off.
- **Verified:** delete route compiles; body type narrowed (`actor` removed).

## 🐛 Correctness

### 5. Scheduler "best time" recommended the wrong day *(Medium)*
- **Bug:** `lib/instagram.ts` built the follower-activity grid with `getUTCDay()` (0=Sun) but `scheduler-helpers.ts` consumed it as 0=Mon — every suggested slot was shifted by the Sun/Mon offset.
- **Change:** Normalised the grid index to Mon-first: `const js = getUTCDay(); const weekday = js === 0 ? 6 : js - 1;`. `lib/instagram.ts`.
- **Verified:** mapping now `grid[0]=Mon … grid[6]=Sun`, matching `DAY_LABELS`; `suggest-time` route compiles (400 validation, not 500).

### 6. Multi-page scheduling cloned a shared `airtable_record_id` *(Medium)*
- **Bug:** `scheduler/schedule-multi` cloned rows via `{...src}` without clearing `airtable_record_id`, so every page-clone carried the original's Airtable id → link-back wrote the published URL to the wrong row (and a unique constraint would fail the insert).
- **Change:** clones now set `airtable_record_id: null`. `scheduler/schedule-multi/route.ts`.
- **Verified:** route compiles (405 on GET).

### 7. Competitor YouTube views zeroed out past 50 videos *(Low)*
- **Bug:** `benchmark/youtube` sent all video IDs in one `videos?id=` call; the API caps `id` at 50, so videos beyond 50 (≈9+ channels) silently read as `views: 0`.
- **Change:** chunk `vidIds` into batches of ≤50 and merge stats. `benchmark/youtube/route.ts`.
- **Verified:** route returns **200 with real view counts** (no regression at the current 12-ID size).

## ⚙️ Performance

### 8. Dead 1-second re-render on the Audience page *(Low)*
- **Bug:** `audience/page.tsx` ran `setInterval(() => setTick(t=>t+1), 1000)` feeding a `void tick; // no-op` — a full Recharts-page re-render every second, forever, for nothing.
- **Change:** removed the `tick` state, the interval, and the no-op. `audience/page.tsx`.
- **Verified:** confirmed `tick`/`setTick` had no other references (Recharts' `tick=` prop is unrelated); page **compiled clean and returned 200**.

### 9. My Day polled the network in hidden background tabs *(Low)*
- **Bug:** `HopeMyDay.tsx` ran chat (15s) and data-pull (20s) polls with no visibility gate, hammering the network even when the tab was backgrounded.
- **Change:** wrapped the two **network** poll callbacks in `if (!document.hidden) …` (left the local clock tick alone — gating it would only make the displayed time stale). `HopeMyDay.tsx`.
- **Verified:** My Day **renders fully with no console errors** after the change.
